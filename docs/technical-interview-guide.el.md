# CodeHub RAG — Οδηγός για την τεχνική συνέντευξη

> Περιγράφει την υλοποίηση του project όπως ελέγχθηκε στις 12 Νοεμβρίου 2026. Ξεχωρίζει την ενεργή διαδρομή Vercel από την παλαιότερη τοπική Python υλοποίηση. Οι αριθμοί του corpus και τα αποτελέσματα αξιολόγησης αφορούν συγκεκριμένη έκδοση, όχι διαρκώς ενημερωμένα στοιχεία του site.

## 1. Πώς παρουσιάζω το project σε ένα λεπτό

«Έφτιαξα έναν Hybrid RAG assistant για το δημόσιο περιεχόμενο της Code.Hub. Συλλέγω τις σελίδες, καθαρίζω και χωρίζω το περιεχόμενό τους σε αποσπάσματα και αποθηκεύω embeddings μαζί με προϋπολογισμένα βάρη BM25 σε PostgreSQL.

Όταν έρχεται μια ερώτηση, ένας query planner αναγνωρίζει αν χρειάζεται αναζήτηση, λίστα ή καταμέτρηση. Στην αναζήτηση συνδυάζω semantic retrieval και BM25 με Reciprocal Rank Fusion. Ανακτώ το ευρύτερο περιεχόμενο των σχετικών σελίδων, ελέγχω αν τεκμηριώνουν απάντηση και στη συνέχεια παράγω κείμενο με παραπομπές.

Το προϊόν περιλαμβάνει και learning advisor: ο χρήστης δηλώνει στόχο, γνώσεις και όριο διάρκειας, λαμβάνει προτάσεις και μπορεί να συγκρίνει δύο συγκεκριμένα μαθήματα. Τα φίλτρα, οι κατάλογοι και η επιλογή πηγών ελέγχονται από τον κώδικα. Το μοντέλο αναλαμβάνει την κατανόηση και τη σύνθεση της γλώσσας.»

## 2. Τι σημαίνει RAG εδώ

**Retrieval-Augmented Generation** σημαίνει ότι πριν παραχθεί η απάντηση ανακτώνται σχετικά στοιχεία από μια εξωτερική συλλογή γνώσης.

Το μοντέλο λαμβάνει την ερώτηση και επιλεγμένο περιεχόμενο του site ως context. Δεν έχουμε κάνει fine-tuning του μοντέλου πάνω στην Code.Hub. Η γνώση της ιστοσελίδας ενημερώνεται με νέα συλλογή και δημοσίευση δεδομένων.

Η ανάκτηση και η παραγωγή έχουν διαφορετικές ευθύνες:

- **Retrieval:** βρίσκει τις πηγές που πιθανόν χρειάζονται.
- **Generation:** συνθέτει απάντηση από τις πηγές που του δόθηκαν.

Αν η ανάκτηση χάσει μια κρίσιμη σελίδα, ακόμη και καλό μοντέλο παραγωγής μπορεί να δώσει ελλιπή απάντηση ή να αρνηθεί να απαντήσει.

## 3. Η τεχνολογική στοίβα

| Κομμάτι | Ενεργή cloud υλοποίηση | Ρόλος |
|---|---|---|
| Frontend | HTML, CSS, vanilla JavaScript | Συνομιλία, wizard, κάρτες, πηγές και συγκρίσεις |
| Backend | Node.js functions στο Vercel | Validation, routing, retrieval και κλήσεις μοντέλων |
| Βάση | PostgreSQL στο Neon | Σελίδες, chunks, vectors, lexical index και snapshots |
| Vector search | Επέκταση pgvector | Exact αναζήτηση με cosine distance |
| Embeddings | `text-embedding-3-small`, 384 διαστάσεις | Διανυσματική αναπαράσταση κειμένου και ερωτήσεων |
| Γλωσσικό μοντέλο | `gpt-6-luna` ως προεπιλογή | Query planning, έλεγχος τεκμηρίωσης, παραγωγή |
| Προετοιμασία δεδομένων | Python | Συλλογή, εξαγωγή, chunking, embeddings, publication |
| Streaming | Server-Sent Events — SSE | Σταδιακή αποστολή απάντησης και metadata |

Η μεταβλητή `OPENAI_MODEL` μπορεί να αλλάξει την προεπιλογή του γλωσσικού μοντέλου. Τα embeddings ορίζονται χωριστά.

### Η διάκριση Python και Node

Το repository περιέχει και τοπική διαδρομή Python/FastAPI, με μοντέλο embeddings `multilingual-e5-small` και τοπικό BM25 index. Αυτή δεν είναι η διαδρομή που χρησιμοποιεί το δημόσιο Vercel chatbot.

Η ενεργή διαδρομή είναι:

```text
Browser → Vercel Node.js API → Neon PostgreSQL και OpenAI → Browser
```

Η Python χρησιμοποιείται για την προετοιμασία των cloud δεδομένων. Δεν χρειάζεται να τρέχει Python server ή τοπικό ONNX μοντέλο μέσα στη Vercel function.

**Στη συνέντευξη:** «Υπάρχουν δύο διαδρομές στο repository. Θα περιγράψω πρώτα αυτή που εξυπηρετεί το δημόσιο deployment.»

### Εξυπηρέτηση μιας ερώτησης

```text

        ↓

        ↓

        ↓

        ↓
```

Δεν ξανασκανάρουμε το site και δεν ξαναφτιάχνουμε τον index σε κάθε ερώτηση.

## 5. Συλλογή και καθαρισμός του περιεχομένου

Η συλλογή ξεκινά από το `robots.txt` και τα δηλωμένα sitemaps. Περιορίζεται στον επιτρεπόμενο ιστότοπο και ελέγχει τους κανόνες πρόσβασης. Διατηρούνται αρχικό HTML, canonical URL, χρόνος συλλογής και hashes περιεχομένου.

Η εξαγωγή αφαιρεί πλοήγηση και στοιχεία που δεν αποτελούν το κύριο περιεχόμενο. Κρατά τίτλους, ενότητες και πληροφορίες που επιτρέπουν να συνδεθεί μια απάντηση με τη σωστή σελίδα.

Δύο πραγματικά προβλήματα που αντιμετωπίστηκαν:

1. **Προτεινόμενα μαθήματα και αγγελίες στο τέλος μιας σελίδας.** Μπορούσαν να κάνουν το σύστημα να αποδώσει χαρακτηριστικά άλλης καταχώρισης στην κύρια σελίδα. Η εξαγωγή αφαιρεί αυτά τα τμήματα.
2. **Επικεφαλίδες μέσα σε tabs.** Η απώλεια της ένδειξης `Prerequisite Knowledge` έκανε τα προαπαιτούμενα λιγότερο σαφή. Οι προσβάσιμες ετικέτες των tabs μετατρέπονται σε επικεφαλίδες των αντίστοιχων ενοτήτων.

Η συλλογή HTML δεν ισοδυναμεί με πλήρη εκτέλεση JavaScript σε browser. Περιεχόμενο που παράγεται αποκλειστικά δυναμικά μπορεί να χρειάζεται διαφορετικό μηχανισμό συλλογής.

**Τι δείχνει αυτό στη συνέντευξη:** η ποιότητα του RAG εξαρτάται και από την ποιότητα των δεδομένων, όχι μόνο από το μοντέλο ή το prompt.

Κώδικας: [extract.py](../src/codehub_rag/extract.py).

## 6. Chunking και parent documents

Ένα **chunk** είναι μικρότερο απόσπασμα μιας σελίδας. Η τρέχουσα cloud προετοιμασία χρησιμοποιεί chunking ανά ενότητα, με στόχο 350 λέξεις και overlap 45 λέξεων μέσα στην ίδια ενότητα.

Αυτά είναι **whitespace-delimited words**, όχι tokens του embedding model. Η παλαιότερη τοπική E5 διαδρομή έχει επιπλέον διαχείριση του ορίου του δικού της tokenizer· δεν πρέπει να μπερδεύουμε τις δύο διαδρομές.

Το overlap διατηρεί λίγο κοινό περιεχόμενο ανάμεσα σε γειτονικά αποσπάσματα, ώστε μια πληροφορία στα όριά τους να μη χάνεται εύκολα.

Κρατάμε επίσης το μεγαλύτερο κείμενο της αρχικής σελίδας ως **parent document**.

> Αναζητούμε μέσω μικρότερων αποσπασμάτων και δίνουμε στο μοντέλο ευρύτερο πλαίσιο από τις αντίστοιχες σελίδες.

Αυτό βοηθά όταν η απάντηση χρειάζεται ταυτόχρονα περιγραφή, διάρκεια και προαπαιτούμενα που βρίσκονται σε διαφορετικά σημεία της ίδιας σελίδας. Το επιπλέον context αυξάνει όμως τα input tokens και μπορεί να προσθέσει θόρυβο.

Κώδικας: [cloud.py — προετοιμασία corpus](../src/codehub_rag/cloud.py).

## 7. Embeddings και semantic search

Το embedding είναι ένα διάνυσμα αριθμών που αναπαριστά χαρακτηριστικά του νοήματος ενός κειμένου. Στο cloud χρησιμοποιούμε 384 διαστάσεις.

Παράδειγμα ερώτησης:

> «Θέλω έναν βοηθό που να απαντά από τα έγγραφα της εταιρείας μου.»

Η ερώτηση μπορεί να είναι κοντά διανυσματικά σε περιγραφή μαθήματος RAG, χωρίς να περιέχει τον όρο «Retrieval-Augmented Generation».

Δημιουργούμε embedding και για την ερώτηση με το ίδιο μοντέλο και τις ίδιες διαστάσεις με τα αποθηκευμένα chunks. Στην PostgreSQL χρησιμοποιούμε cosine distance μέσω pgvector. Μικρότερη απόσταση σημαίνει μεγαλύτερη εγγύτητα σύμφωνα με αυτή τη μετρική.

Τα E5 vectors της τοπικής διαδρομής και τα OpenAI vectors της cloud διαδρομής δεν είναι συμβατά μόνο και μόνο επειδή έχουν 384 διαστάσεις. Ανήκουν σε διαφορετικούς χώρους αναπαράστασης.

### Γιατί exact search;

Η ενεργή αναζήτηση δεν χρησιμοποιεί HNSW ή IVFFlat approximate index. Στο σημερινό μικρό corpus το exact search είναι απλό και αποφεύγει την απώλεια recall που μπορεί να προκύψει από approximate αναζήτηση. Δεν αποτελεί υπόσχεση ότι θα έχει την ίδια συμπεριφορά σε εκατομμύρια chunks.

Σε μεγαλύτερο corpus θα μετρούσαμε latency και recall και θα αξιολογούσαμε approximate indexing.

Κώδικας: [provider.js — embeddings](../web/lib/provider.js), [store.js — vector retrieval](../web/lib/store.js).

## 8. BM25 και γιατί αποθηκεύουμε τα στατιστικά

Το BM25 είναι lexical retrieval: αξιολογεί πόσο σχετικοί είναι οι όροι μιας ερώτησης με ένα απόσπασμα. Είναι χρήσιμο για ακριβείς τεχνικούς όρους, τίτλους και κωδικούς, όπως `PL/SQL`, `C#` ή `LangChain`.

Βασικές έννοιες:

| Όρος | Σημασία |
|---|---|
| TF | Πόσες φορές εμφανίζεται ένας όρος σε ένα chunk |
| DF | Σε πόσα chunks εμφανίζεται ο όρος |
| IDF | Βάρος που σχετίζεται με τη σπανιότητα του όρου στο corpus |
| Document length | Μήκος του chunk μετά την tokenization |
| Average length | Μέσο μήκος των chunks |

Εδώ το «document» των BM25 στατιστικών αντιστοιχεί σε chunk, όχι σε ολόκληρη ιστοσελίδα.

Οι παράμετροι είναι `k1 = 1.5` και `b = 0.75`. Το `k1` ελέγχει τον κορεσμό της συχνότητας όρου και το `b` τη διόρθωση για το μήκος του κειμένου.

Η cloud υλοποίηση αποθηκεύει στατιστικά και προϋπολογισμένα βάρη ανά όρο και chunk στην PostgreSQL. Κατά την ερώτηση αθροίζονται τα αποθηκευμένα βάρη για τους μοναδικούς όρους του query.

```text
Offline: corpus → DF, IDF, μήκη, βάρη ανά όρο/chunk → PostgreSQL
Online: όροι ερώτησης → ανάγνωση και άθροιση αποθηκευμένων βαρών
```

Δεν επανυπολογίζεται ολόκληρος ο index ανά request. Τα στατιστικά συνδέονται με το snapshot του corpus.

Ο tokenizer κανονικοποιεί πεζά/κεφαλαία και ελληνικούς τόνους, αφαιρεί επιλεγμένες stopwords και διατηρεί τεχνικούς όρους. Υπάρχει και περιορισμένο δίγλωσσο glossary για επέκταση ερωτημάτων. Δεν είναι πλήρης μετάφραση ή γενική κάλυψη όλων των συνωνύμων.

Κώδικας: [cloud.py — corpus_statistics και postings](../src/codehub_rag/cloud.py), [lexical.js](../web/lib/lexical.js).

## 9. Hybrid retrieval και Reciprocal Rank Fusion

Τα embeddings βοηθούν στις παραφράσεις. Το BM25 βοηθά στους συγκεκριμένους όρους. Συνδυάζουμε τις δύο προσεγγίσεις αντί να περιμένουμε ότι μία θα καλύψει όλες τις ερωτήσεις.

Η ενεργή διαδρομή παίρνει έως 100 υποψήφια chunks από κάθε retriever και μετατρέπει τις κατατάξεις σε μοναδικές canonical σελίδες.

Χρησιμοποιούμε **Reciprocal Rank Fusion — RRF**:

```text
score(σελίδα) = άθροισμα 1 / (60 + θέση σε κάθε κατάταξη)
```

Οι θέσεις ξεκινούν από το 1. Μια σελίδα που εμφανίζεται ψηλά σε περισσότερες κατατάξεις ενισχύεται.

Δεν προσθέτουμε απευθείας cosine similarity και BM25 score: οι δύο τιμές έχουν διαφορετικές κλίμακες. Το RRF χρησιμοποιεί θέσεις και αποφεύγει την ανάγκη άμεσης κανονικοποίησης των scores.

Η υλοποίηση προσθέτει κατατάξεις για την προτιμώμενη κατηγορία, ώστε να ενισχύονται σχετικές σελίδες. Αυτό είναι προτίμηση κατάταξης. Ένα ρητά επιλεγμένο UI category filter εφαρμόζεται αποκλειστικά όταν συμφωνεί με την κατηγορία του query plan.

Ανακτούμε τις πρώτες 12 parent σελίδες, έως 16.000 χαρακτήρες ανά σελίδα. Όπου επιτρέπεται, μπορεί να προστεθεί και η σελίδα επικοινωνίας. Δεν έχουμε ξεχωριστό cross-encoder reranker στην τρέχουσα υλοποίηση.

Κώδικας: [store.js](../web/lib/store.js), [lexical.js — fuse](../web/lib/lexical.js).

## 10. Query planner: «ποιες» και «πόσες»

Πριν από την κανονική αναζήτηση, μια κλήση στο γλωσσικό μοντέλο ερμηνεύει την ερώτηση και επιστρέφει αυστηρά δομημένο JSON.

```json
{
  "operation": "search",
  "collection": "course",
  "constrained": true,
  "query": "RAG courses for someone with Python and SQL",
  "next_page": false,
  "language": "el"
}
```

| Ερώτηση | Διαδρομή |
|---|---|
| «Πόσα μαθήματα υπάρχουν συνολικά;» | Στοιχεία καταλόγου και SQL καταμέτρηση |
| «Ποια μαθήματα υπάρχουν;» | Κατάλογος από τη βάση, 10 ανά σελίδα |
| «Ποια μαθήματα αφορούν RAG;» | Αναζήτηση με περιορισμούς |
| «Πόσα μαθήματα RAG είναι έως 24 ώρες;» | Αναζήτηση· δεν επιστρέφεται το συνολικό πλήθος του καταλόγου |

Το μοντέλο επιλέγει μεταξύ `search`, `list` και `count`. Δεν παράγει αυθαίρετη SQL. Ο server ελέγχει το αποτέλεσμα και εκτελεί συγκεκριμένες λειτουργίες που έχουμε γράψει εμείς.

Ερωτήσεις με περιορισμούς δεν επιτρέπεται να μετατραπούν σιωπηρά σε μη φιλτραρισμένη λίστα ή καταμέτρηση. Παράλληλα, η ανάκτηση ενός υποσυνόλου δεν αποδεικνύει το ακριβές πλήθος όλων των αποτελεσμάτων που ικανοποιούν έναν σύνθετο περιορισμό.

Ο planner βλέπει μέχρι τέσσερα προηγούμενα μηνύματα, περικομμένα σε 1.400 χαρακτήρες το καθένα. Αυτό βοηθά στις συνέχειες, αλλά δεν είναι απεριόριστη μνήμη και μπορεί να χάσει ασαφείς αναφορές.

Κώδικας: [planner.js](../web/lib/planner.js).

## 11. Έλεγχος τεκμηρίωσης και παραγωγή απάντησης

Μετά την ανάκτηση, ξεχωριστή κλήση μοντέλου ελέγχει αν οι πηγές επαρκούν:

```json
{
  "answerable": true,
  "reason": "supported",
  "source_ids": [1, 3]
}
```

Ο server επιβεβαιώνει ότι τα IDs αντιστοιχούν σε πηγές που πράγματι δόθηκαν. Άκυρη ή μη ολοκληρωμένη απάντηση του ελέγχου δεν αντιμετωπίζεται ως έγκριση.

Για σχετική ερώτηση με ανεπαρκή τεκμηρίωση επιτρέπεται μία ακόμη ανάκτηση από επόμενα αποτελέσματα της ίδιας κατάταξης και επανάληψη του ελέγχου. Δεν είναι απεριόριστο agent loop και δεν ξαναγράφει διαρκώς το query.

Αν τα στοιχεία παραμένουν ανεπαρκή, επιστρέφεται προκαθορισμένο μήνυμα. Αν επαρκούν, έως 10 επιλεγμένες πηγές περνούν στην παραγωγή με συνεπή αρίθμηση.

Η παραγωγή λαμβάνει την ερώτηση, το query plan, τις πηγές και μέχρι οκτώ προηγούμενα μηνύματα. Ζητείται να τεκμηριώνει ισχυρισμούς και να αναγνωρίζει ελλείψεις.

Η προεπιλογή είναι `gpt-6-luna`. Planning και evidence check χρησιμοποιούν `low` reasoning effort. Η παραγωγή χρησιμοποιεί `medium` για constrained queries και `low` για τα υπόλοιπα. Το όριο παραγωγής είναι 3.000 output tokens, συμπεριλαμβανομένων reasoning tokens όπου εφαρμόζεται.

### Τι εγγυάται και τι δεν εγγυάται ο έλεγχος

Ο έλεγχος περιορίζει την παραγωγή χωρίς πηγές. Δεν αποδεικνύει ότι κάθε τελική πρόταση είναι σωστή. Το ίδιο μοντέλο μπορεί να αξιολογήσει λάθος την επάρκεια ή να συνθέσει λάθος μια λεπτομέρεια.

Στο τέλος κρατάμε μόνο γνωστές πηγές που παραπέμπονται μέσα στην απάντηση. Αυτό ελέγχει τη συνέπεια των IDs, όχι ότι κάθε citation συνεπάγεται λογικά τον σχετικό ισχυρισμό. Δεν υπάρχει γενικός τελικός έλεγχος κάθε ισχυρισμού μετά την παραγωγή.

Κώδικας: [grounding.js](../web/lib/grounding.js), [provider.js](../web/lib/provider.js), [citations.js](../web/public/citations.js).

## 12. Πώς λειτουργεί ο learning advisor

Ο χρήστης δηλώνει στόχο, γνώσεις και προαιρετικό όριο συνολικής διάρκειας ανά μάθημα. Οι τρεις προτάσεις στο wizard είναι παραδείγματα· το πεδίο στόχου είναι ελεύθερο.

Τα άγνωστα προσόντα δεν πρέπει να παρουσιάζονται ως ελλείψεις. Αν ο χρήστης δεν έχει αναφέρει αν γνωρίζει APIs, το σύστημα πρέπει να ζητήσει διευκρίνιση. Αν δηλώσει ότι δεν γνωρίζει Python, αυτό αποτελεί συγκεκριμένο στοιχείο του προφίλ.

Η διάρκεια, το επίπεδο, το κοινό και τα προαπαιτούμενα εξάγονται από το αποθηκευμένο κείμενο της πηγής. Ο σαφής διαχωρισμός required/beneficial διατηρείται όπου υπάρχει αντίστοιχη σήμανση. Δεν επινοούμε τέτοια δομή για κάθε κείμενο.

### Το όριο ωρών εφαρμόζεται από τον κώδικα

Για προτάσεις μαθημάτων δημιουργείται λίστα επιτρεπόμενων URLs με επιβεβαιωμένη διάρκεια εντός ορίου. Η λίστα εφαρμόζεται και στους δύο retrievers, καθώς και στην επαναληπτική ανάκτηση.

Άγνωστη ή μηδενική διάρκεια δεν περνά το φίλτρο. Οι 24 ώρες σημαίνουν έως 24 συνολικές ώρες ανά μάθημα, όχι εβδομαδιαία διαθεσιμότητα ή άθροισμα όλων των προτάσεων.

### Η σύγκριση διαβάζει τα επιλεγμένα μαθήματα

Όταν ο χρήστης επιλέγει δύο κάρτες, στέλνονται τα δύο canonical URLs και το snapshot ID. Το backend διαβάζει αυτές ακριβώς τις parent σελίδες, παρακάμπτοντας planner και similarity search. Συνεχίζει όμως να εφαρμόζει evidence check και παραγωγή.

Μια επιλεγμένη σύγκριση μπορεί να περιέχει μάθημα πάνω από το όριο ωρών. Δεν κρύβουμε το επιλεγμένο μάθημα· η απάντηση πρέπει να επισημαίνει την υπέρβαση. Το φίλτρο περιορίζει τις προτάσεις, όχι το τι μπορεί να συγκρίνει ρητά ο χρήστης.

Οι κάρτες και ο πίνακας χρησιμοποιούν πεδία της πηγής. Η καταλληλότητα είναι εκτίμηση του βοηθού και δεν αποτελεί πιστοποίηση, επίσημη διαδρομή μάθησης ή εγγύηση εργασίας.

Κώδικας: [learning.js](../web/lib/learning.js), [cloud.js](../web/lib/cloud.js), [app.js](../web/public/app.js).

## 13. Snapshots και ενημέρωση δεδομένων

Ένα snapshot συνδέει συγκεκριμένο corpus με τα embeddings, τα BM25 δεδομένα και τις ρυθμίσεις του. Κάθε αναζήτηση χρησιμοποιεί το ίδιο snapshot ID σε όλα τα σχετικά queries.

Η δημοσίευση ελέγχει hashes, πληρότητα embeddings και πλήθη εγγραφών πριν ενεργοποιήσει τη νέα έκδοση μέσα σε συναλλαγή. Η προηγούμενη παραμένει διαθέσιμη. Έτσι δεν αναμειγνύονται vectors μιας έκδοσης με lexical δεδομένα άλλης.

Τα embeddings επαναχρησιμοποιούνται μέσω cache που λαμβάνει υπόψη το μοντέλο, τις διαστάσεις και το ακριβές input hash. Δεν χρειάζεται κάθε επανεκτέλεση να πληρώνει για τα ίδια κείμενα.

Η έκδοση που δημοσιεύτηκε στις 12/11/2026 περιλαμβάνει:

- 167 parent documents και 1.754 chunks.
- 46 μαθήματα, από τα οποία 45 με θετική δημοσιευμένη διάρκεια.
- Πηγές που συλλέχθηκαν στις 10/11/2026 και επανεπεξεργάστηκαν με διορθωμένη εξαγωγή.

Η ύπαρξη μιας καταχώρισης δεν αποδεικνύει ότι μια θέση ή εκδήλωση παραμένει ενεργή. Η ημερομηνία συλλογής δεν είναι ημερομηνία τελευταίας αλλαγής της ίδιας της σελίδας.

## 14. Streaming, ιστορικό και λειτουργικοί έλεγχοι

Ο browser στέλνει `POST /api/chat`. Η απάντηση επιστρέφει ως SSE, με events για στάδιο εργασίας, πηγές, τμήματα κειμένου, learning metadata και ολοκλήρωση.

Το SSE επιτρέπει σταδιακή εμφάνιση της απάντησης. Δεν αφαιρεί τον χρόνο που απαιτείται για planning, retrieval και evidence check πριν αρχίσει η παραγωγή.

Οι συνομιλίες και το προφίλ διατηρούνται στο `localStorage` του browser. Περιορισμένο ιστορικό και το τρέχον προφίλ αποστέλλονται στο backend και στις αντίστοιχες κλήσεις μοντέλου. Η τοπική αποθήκευση δεν σημαίνει ότι το περιεχόμενο δεν φεύγει από τη συσκευή κατά την επεξεργασία.

Υπάρχουν validation για μήκη και ρόλους μηνυμάτων, χρονικά όρια, ακύρωση εργασίας και καθαρισμένα μηνύματα σφαλμάτων. Τα credentials μένουν στον server.

Τα όρια αιτημάτων αποθηκεύονται στην PostgreSQL ώστε να εφαρμόζονται και ανάμεσα σε διαφορετικά serverless instances. Η διεύθυνση πελάτη χρησιμοποιείται σε hashed counter. Αυτό δεν είναι πλήρες authentication ούτε απόλυτο χρηματικό όριο.

Το περιεχόμενο του site αντιμετωπίζεται ως μη έμπιστο υλικό αναφοράς και όχι ως εντολές. Τα αυστηρά schemas, τα περιορισμένα actions και η ασφαλής απόδοση κειμένου μειώνουν κινδύνους· δεν αποτελούν απόδειξη πλήρους προστασίας από prompt injection.

## 15. Κόστος και καθυστέρηση

| Διαδρομή | Συνήθεις κλήσεις μοντέλων |
|---|---|
| Κανονική επιτυχής hybrid ερώτηση | Planner + query embedding + evidence check + generation |
| Ανάκτηση επιπλέον στοιχείων | Μπορεί να προστεθεί ένας ακόμη evidence check |
| Γενική λίστα ή καταμέτρηση | Planner και στη συνέχεια λειτουργία βάσης, χωρίς generation |
| Κουμπί επόμενης σελίδας | Συγκεκριμένη λειτουργία καταλόγου, χωρίς planner |
| Επιλεγμένη σύγκριση | Evidence check + generation, χωρίς planner ή embedding |

Δεν έχουν όλες οι ερωτήσεις ίδιο κόστος. Τα μεγαλύτερα parent contexts αυξάνουν input tokens. Οι επιπλέον έλεγχοι προσθέτουν χρόνο, αλλά μπορούν να περιορίσουν αστήρικτες απαντήσεις.

Στις τρεις δημόσιες δοκιμές αυτής της έκδοσης οι χρόνοι ήταν περίπου 6–21 δευτερόλεπτα. Είναι παρατηρήσεις από συγκεκριμένες δοκιμές, όχι SLA ή γενικός μέσος όρος.

Η φιλοξενία σε free tiers δεν κάνει δωρεάν τις κλήσεις embeddings και γλωσσικού μοντέλου. Το τρέχον αναφερόμενο token usage της απάντησης περιλαμβάνει τις γλωσσικές κλήσεις της διαδρομής, όχι το query embedding.

## 16. Αξιολόγηση και ειλικρινής παρουσίαση ορίων

Οι αυτοματοποιημένοι έλεγχοι καλύπτουν validation, retrieval στη βάση, citations, streaming, pagination, επιλογή μαθημάτων και εφαρμογή του φίλτρου διάρκειας.

Οι πραγματικές δοκιμές εξετάζουν περιεχόμενο απαντήσεων. Για τον learning advisor αξιολογήθηκαν έξι περιπτώσεις ανάπτυξης, έγινε επανάληψη 30 ερωτήσεων και εκτελέστηκαν τρεις δημόσιες δοκιμές στο Vercel.

Το ότι ένα request ολοκληρώθηκε με HTTP 200 δεν σημαίνει ότι η απάντησή του ήταν σωστή. Αυτές οι ερωτήσεις χρησιμοποιήθηκαν κατά την ανάπτυξη και δεν αποτελούν ανεξάρτητο held-out benchmark.

Καταγεγραμμένος περιορισμός: σε συνέχεια ερώτησης για τοποθεσίες αγγελιών, το retrieval έχασε τεκμηρίωση για μία σχετική θέση. Επίσης, ο οπτικός έλεγχος της νέας εμφάνισης δεν ολοκληρώθηκε λόγω περιορισμού του browser tool· οι αλληλεπιδράσεις ελέγχθηκαν με DOM tests.

Μετρήσεις που θα χρησιμοποιούσα σε επόμενο στάδιο:

- **Recall@k:** πόσες από τις γνωστές σχετικές πηγές ανακτήθηκαν στις πρώτες k.
- **MRR:** πόσο ψηλά εμφανίζεται η πρώτη σχετική πηγή.
- **Ορθότητα απάντησης:** αν καλύπτει σωστά το ζητούμενο.
- **Τεκμηρίωση ισχυρισμών:** αν οι παραπομπές στηρίζουν όσα γράφονται.
- **Σωστή αποχή:** αν αναγνωρίζει πραγματικά ανεπαρκή στοιχεία.
- **Latency και κόστος:** ανά διαδρομή και τύπο ερώτησης.

Αναφορές: [γενική αξιολόγηση](../reports/chatbot-quality-2026-11-12.html), [learning advisor](../reports/learning-advisor-2026-11-12.html).

## 17. Πιθανές ερωτήσεις συνέντευξης και απαντήσεις

### Γιατί δεν αρκεί μόνο ένα LLM;

«Χρειάζομαι απαντήσεις που να βασίζονται σε συγκεκριμένο περιεχόμενο της εταιρείας, με πηγές και δυνατότητα ενημέρωσης. Το RAG παρέχει εξωτερικό context χωρίς να απαιτεί fine-tuning για κάθε αλλαγή.»

### Γιατί hybrid και όχι μόνο semantic search;

«Οι παραφράσεις και οι ακριβείς τεχνικοί όροι έχουν διαφορετικές ανάγκες. Τα embeddings βοηθούν στη σημασιολογική συνάφεια και το BM25 στις συγκεκριμένες λέξεις. Η χρησιμότητα του συνδυασμού πρέπει να μετριέται σε evaluation set.»

### Γιατί PostgreSQL;

«Το pgvector μου επιτρέπει να κρατάω vectors μαζί με σελίδες, metadata, lexical δεδομένα και snapshots στην ίδια βάση. Αυτό απλοποιεί τις συναλλαγές και τη συνέπεια εκδόσεων για το μέγεθος του project.»

### Γιατί δεν βγάζεις πλήθος από τα αποτελέσματα retrieval;

«Το retrieval επιστρέφει υποψήφια σχετικά αποτελέσματα, όχι απαραίτητα ολόκληρο το σύνολο. Για γενικά πλήθη χρησιμοποιώ τον κατάλογο και λειτουργίες βάσης. Για σύνθετα φίλτρα δεν παρουσιάζω το μέγεθος του ανακτημένου υποσυνόλου ως ακριβές σύνολο.»

### Έλυσες τα hallucinations;

«Όχι πλήρως. Χρησιμοποιώ επιλεγμένες πηγές, evidence gate, περιορισμένη επανάληψη retrieval και παραπομπές. Χρειάζεται ακόμη αξιολόγηση της ορθότητας και της στήριξης των ισχυρισμών.»

### Είναι agent;

«Έχει model-based σχεδιασμό με περιορισμένες λειτουργίες και συγκεκριμένη ροή. Δεν είναι γενικός αυτόνομος agent με απεριόριστο loop ή αυθαίρετη εκτέλεση εργαλείων.»

### Τι θα βελτίωνες πρώτο;

«Θα δημιουργούσα ανεξάρτητο evaluation set, ιδιαίτερα για follow-ups, αμφίσημες οντότητες και σύνθετους περιορισμούς. Θα εντόπιζα αν κάθε αποτυχία προέρχεται από extraction, retrieval ή generation και μετά θα επέλεγα την παρέμβαση. Reranking, structured filters και διαφορετικά μοντέλα είναι υποψήφιες βελτιώσεις που χρειάζονται μέτρηση.»

## 19. Σενάριο demo τριών λεπτών

1. Ρωτάω «Πόσα trainings υπάρχουν;» και εξηγώ γιατί η καταμέτρηση χρησιμοποιεί τον κατάλογο.
2. Ρωτάω «Θέλω έναν βοηθό που να απαντά από τα εταιρικά έγγραφα» και δείχνω τη σημασιολογική σύνδεση με RAG.
3. Ανοίγω το «Το επόμενο skill μου», δηλώνω Python/SQL και όριο 24 ωρών ανά μάθημα.
4. Επιλέγω δύο διαθέσιμες κάρτες για σύγκριση και δείχνω τα δημοσιευμένα στοιχεία και τις πηγές.
5. Ανοίγω το «Πώς προέκυψε αυτή η απάντηση;» και ξεχωρίζω τα λειτουργικά metadata από εσωτερικό reasoning, το οποίο δεν εμφανίζεται.
6. Κλείνω με έναν γνωστό περιορισμό και το πώς θα τον μετρούσα πριν τον διορθώσω.

Η σημαντικότερη διάκριση που πρέπει να μπορείς να εξηγήσεις είναι: **ποια απόφαση παίρνει το μοντέλο, ποιον κανόνα εφαρμόζει ο κώδικας και ποιο δεδομένο προέρχεται από την πηγή.**
